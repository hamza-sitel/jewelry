- One `createOperation(request)` command instead of positional arguments.

## 4. DTO lesson — design the request yourself

A DTO is a Data Transfer Object. It is the shape of data sent across an application boundary. It is not the database table and it is not the Angular form itself.

Imagine the operator sells two pieces of product 10 and adds a note. What does the browser know?

- Which product was selected: `productId`.
- Which action is requested: `type`.
- How many pieces move: `quantity`.
- Optional explanation: `notes`.

The browser must not decide the new stock number, because the browser may be stale or manipulated. The server/mock command calculates the stock change from the latest product stock.

The request DTO is:

```ts
export interface CreateStockOperationRequest {
  productId: number;
  type: StockOperationType;
  quantity: number;
  notes: string | null;
}
```

### Understand every field

| Field | Why it belongs in the request | Validation |
|---|---|---|
| `productId` | Identifies the product being changed | Positive safe integer; product must exist and be active |
| `type` | Says whether stock increases or decreases | One of `PURCHASE`, `SALE`, `MANUAL_ADD`, `MANUAL_REMOVE` |
| `quantity` | Number of whole pieces moving | Positive safe integer; decimals and zero are rejected |
| `notes` | Optional audit explanation | Text or `null`, maximum 500 characters |

### Why these fields are NOT in the request

- `id`: generated by the API/mock when it records the operation.
- `createdAt`: generated by the API/mock so the client cannot choose a false timestamp.
- `previousStock`: read from the current product state.
- `newStock`: calculated by the stock-operation logic.
- `productName` and `barcode`: read from the product record, not trusted from the browser.

This is an important security and correctness principle: **send the intent; let the trusted application layer calculate the result.**

## 5. Response model — the server's answer

The server/mock returns a `StockOperationResponse`:

```ts
export interface StockOperationResponse {
  id: number;
  productId: number;
  productName: string;
  barcode: string;
  type: StockOperationType;
  quantity: number;
  previousStock: number;
  newStock: number;
  createdAt: string;
  notes: string | null;
}
```

The response contains both the original request information and server-generated facts. The page uses `newStock` to show the result, and Stock History uses the response to display an immutable history record.

There is no `UpdateStockOperationRequest`: stock history is an audit trail, so a recorded movement should not be edited like a product description. If a movement was wrong, a correcting manual operation can be recorded instead.

There is no separate `BarcodeLookupResponse` in this phase. Barcode lookup returns the same `ProductResponse` used by product details because it is returning a product, not a new kind of resource. Creating duplicate response types with identical fields would add maintenance without adding meaning.

## 6. The DTO-to-storage flow

The flow after this update is:

```text
Stock Operation page / Barcode Scanner
             |
             | CreateStockOperationRequest
             v
      StockOperationService
             |
             | validates request shape
             v
      STOCK_OPERATION_DATA_SOURCE
             |
       Mock implementation now
             |
             +---- reads current product
             +---- checks product is active
             +---- calculates new whole-piece quantity
             +---- updates product stock
             +---- writes StockOperationResponse to history
             |
             v
      StockOperationResponse
             |
             +---- success message
             +---- Stock History row
             +---- Product Details history
```

The service validates the incoming request shape. The mock data source simulates the stock-operation endpoint and checks current stock. A future `ApiStockOperationDataSource` will send one HTTP `POST` request to Spring Boot.

### Why the mock has rollback logic

Browser `localStorage` does not provide database transactions. The mock first updates product stock and then tries to save the history row. If history persistence fails, it attempts to restore the previous product quantity. If rollback also fails, it displays an explicit error saying the product must be inspected before retrying.

This is a compensating action, not a true database transaction. In Spring Boot, the correct implementation is one service method using `@Transactional`, so the product update and history insert either both commit or both roll back.

## 7. The four stock movement rules

All inventory movements are recorded as integer pieces, regardless of tracking mode.

| Operation | Calculation | Example from stock 8 with quantity 3 |
|---|---:|---:|
| `PURCHASE` | current + quantity | 11 |
| `MANUAL_ADD` | current + quantity | 11 |
| `SALE` | current - quantity | 5 |
| `MANUAL_REMOVE` | current - quantity | 5 |

The resulting stock cannot be negative.

For a weighted product with weight 2.590 g per piece and quantity 4, the total recorded product weight is 10.360 g. Selling two pieces changes quantity from 4 to 2; the product's derived total weight becomes 5.180 g. The stock-operation DTO still sends `quantity: 2`; it does not send or update grams. This preserves the agreed rule that stock movements are in pieces, not gram-based movements.

## 8. Stock History behavior

The Stock History page now filters the full in-memory operation list before pagination:

1. Search by product name, barcode, notes or product ID.
2. Filter by operation type.
3. Filter from a date and/or to a date (inclusive).
4. Sort newest-first or oldest-first.
5. Display 20 filtered rows per page.
6. Reset to page 1 whenever filters change.
7. Click the product name to open that product's details.

The order matters. Filtering and sorting happen first; pagination slices the final filtered list afterward. That prevents a search from searching only the current page.

This is client-side pagination because the mock source returns the full localStorage list. When the backend exists and the history becomes large, we can add a query DTO and `PageResponse<T>` for server-side pagination. We are deliberately not adding unused page DTOs before an API requires them.

## 9. Barcode scanner behavior

A USB barcode scanner normally behaves like a keyboard: it types the barcode into the focused input and sends Enter. The form's `(ngSubmit)` handles Enter; a separate key listener is not needed.

The scanner flow is:

1. Focus the input when the page opens.
2. Normalize the barcode by trimming spaces and converting it to uppercase.
3. Call `ProductService.getProductByBarcode()`.
4. Display the product or an unknown/archived message.
5. Build the same `CreateStockOperationRequest` used by the Stock Operation page.
6. Prevent duplicate submissions while saving.
7. Update the visible quantity from the returned `StockOperationResponse`.
8. Return focus to the scanner input.

The future API contract is `GET /api/products/barcode/{barcode}`, returning `ProductResponse`.

## 10. Proposed Spring Boot API contract

These are proposed endpoints; the backend is not connected yet.

| Purpose | Method | Endpoint | Body/response |
|---|---|---|---|
| All history | GET | `/api/stock-operations` | `StockOperationResponse[]` |
| Product history | GET | `/api/stock-operations?productId=10` | `StockOperationResponse[]` |
| Create movement | POST | `/api/stock-operations` | `CreateStockOperationRequest` → `StockOperationResponse` |
| Barcode lookup | GET | `/api/products/barcode/JWL000010` | `ProductResponse` |

A matching Java request DTO could look like:

```java
public record CreateStockOperationRequest(
    @NotNull @Positive Long productId,
    @NotNull StockOperationType type,
    @NotNull @Positive Integer quantity,
    @Size(max = 500) String notes
) {}
```

The Spring service would load the product, validate its status and available stock, calculate the new quantity, save the product and movement record in one `@Transactional` method, then return a response DTO. Do not let Angular send `previousStock` or `newStock` as trusted inputs.

## 11. Why SOLID / DRY / KISS fit here

- **SRP:** the page collects input; `StockOperationService` validates the command shape; the data-source adapter performs the selected mock/API operation.
- **DIP:** the service depends on `STOCK_OPERATION_DATA_SOURCE`, not directly on browser storage.
- **OCP:** the mock source can later be replaced by an API source implementing the same contract.
- **ISP:** this data-source contract exposes only the stock-history and stock-operation actions required here.
- **DRY:** both manual stock entry and barcode scanning build the same request DTO and call the same service method.
- **KISS:** only one create request DTO is needed. No update/delete DTO is invented for immutable audit history.
